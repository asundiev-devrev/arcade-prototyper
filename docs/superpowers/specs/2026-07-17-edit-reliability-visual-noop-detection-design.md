# Edit reliability — "when the agent says it changed the screen, the screen changed"

**Date:** 2026-07-17 (rev. 3 — a SECOND cold review found rev-2's Important-E fix was itself unsound (self-poisoned the compare → fired on 100% of edits) + 4 more real gaps; all folded in. Key rev-3 changes: baseline captured ONLY at-rest (`editCycleActive===false`), never from the probe (fixes the self-poison); fingerprint drops live `textContent` + awaits `document.fonts.ready` and rides its OWN `frame-fingerprint` message (so live clocks don't make it never-fire and it doesn't stall the swap); `reconnect` must be exported + fire only on `phase==="done"`; narration-gate keys on the SUMMARY line only and biases toward FIRING; one-shot keyed on the user-turn lineage, not the rotating sessionId. Rev-2 folded 2 Criticals + 3 Importants: narration-gate, `document.body` scope, buffer-to-turn-end + client reconnect.)
**Status:** design for review
**Umbrella:** "edit reliability" (beta feedback, gil.zissu). **Sixth sibling.** The fifth (agent honesty) closed the *invented-prop* class — the agent writing a prop the kit doesn't have. This one closes the *next* class the manual gate surfaced: **the agent writes a REAL, valid prop the component silently ignores, so the code changes but the rendered screen does not — and the agent reports success.**

## The experience goal

> **A designer should be able to trust "done." When the agent says it changed how something looks or lays out, the pixels should actually move. When an edit changes the code but nothing on screen changes, Studio notices — tries once to make it real, and if it still can't, says so plainly instead of a false "done."**

## Live repro (root-caused, confirmed against code + the on-disk frame)

Project `computer-skills-filtering-proto`, frame `01-computer-settings`, `pages/Preferences.tsx`. Two-step:
1. User: "Change all selects on the Preferences page to multi-select." Agent correctly switched three `Select.Root` → `ToggleGroup type="multiple"` (the *right* multi-select — feature 5 working: no invented prop, no false block). But a horizontal segmented control holding long timezone strings is very wide → it squeezed the cards. A layout-quality miss, not a lie.
2. User: "Can you make these togglegroups vertical? They're currently squeezing the rest of the content in cards." Agent wrote `orientation="vertical"` on all three `ToggleGroup.Root` (**verified on disk** — the file genuinely changed, not a phantom edit) and reported: *"ToggleGroups now stack vertically — stops squeezing horizontal space."* **The page looked exactly as before.**

**Root cause (confirmed against `~/arcade-gen/src/components/ui/ToggleGroup/ToggleGroup.tsx`):** the kit's ToggleGroup Root is hardcoded `inline-flex items-center` and has **no styling that responds to `orientation`**. `orientation` is a *real* Radix prop (Radix accepts it — it governs arrow-key nav direction), so it is honest for the agent to try it and it passes every existing guard: it is not an invented prop (feature 5's hook is silent — correctly), and `Preferences.tsx`'s content-hash *did* change (the phantom-edit contract is silent — correctly). The prop was **swallowed**: accepted, stored, zero pixels moved.

**Why the existing checks can't catch it.** Studio already has the *file-level* twin of this feature: `frameChangeContract.ts` snapshots `frames/`+`shared/` by content hash before/after a turn, and `phantomEditRetry.ts` re-runs the turn once with a corrective when the agent claimed an edit but **no file moved**, then shows the `NO_CHANGES_TRAILER` banner. That fires on "no file changed." Here the file **did** change — so it passes. The missing check is the *visual* one: **the file moved but the rendered frame did not.**

## Scope decision

Build the visual sibling of the phantom-edit check. Behavior chosen with the user: **auto-retry once, then warn** (mirror the phantom-edit precedent). Detection lives where pixels exist (the browser); the corrective turn is server-owned and invisible (like phantom retry); the final "still nothing changed" nudge is client-side (only the browser can see it).

**Explicitly OUT:**
- **Fidelity / "does it match the Figma"** — the render-verify keystone that *scores* similarity to a target. This feature is the strictly-cheaper binary "**did anything visible change at all**," not "is it right." (See auto-memory `studio-fidelity-metric-keystone` — that keystone stays unbuilt; this is not it.)
- **Fixing the kit's ToggleGroup to honor `orientation`** — a real kit gap, tracked separately; the user may take the 2-minute kit fix independently. This feature must work regardless of whether that specific gap is closed, because the *class* (any real-but-swallowed prop on any component) is what we're closing.
- **Adding a general prop typechecker** — out; this is a runtime-render check, not a static one.

## Honest coverage bound (state plainly, like the feature-5 bound)

This catches **"the agent claimed a visual change, but the at-rest rendered frame is pixel-identical."** It does NOT:
- **Catch a wrong-but-visible change** (agent made the box blue when you wanted red — pixels *did* move; this feature is silent, correctly — that's the fidelity keystone's job).
- **Fire on a legitimate non-visual edit.** Wiring an `onClick`, adding an `aria-label`, or changing a data attribute legitimately leaves the at-rest screen unchanged. Early designs would have flagged these too and burned a wasted corrective turn on the most common activity in a prototyping tool (wiring interactions). **Rev-2 fix (the load-bearing one):** the trigger is **narration-gated** — it fires ONLY when the agent's own turn narration *claimed a visual/layout change* AND the fingerprint is unchanged. A behavior edit narrates behavior ("wired the button to open the modal") → no visual claim → never triggers → no wasted turn. The swallowed-prop repro narrates a visual claim ("ToggleGroups now stack vertically") → triggers. Narration-gating is what makes "auto-retry once" both safe and cheap. The safe direction is the **opposite** of the write-time hooks: a **missed** no-op (we fail to warn) is fine; a **false** "nothing changed" claim over a real visible change is the cardinal sin, so the fingerprint errs toward "changed" and any non-determinism fails safe (no warning).

**Coverage the narration-gate trades away (accepted):** an agent that swallows a prop AND *also* fails to claim it visually (narrates vaguely) won't trigger. Accepted — the alternative (fire on every fingerprint match) false-fires on the common behavior-edit case, which is worse. The gate matches the repro (the agent DID claim "now stack vertically") and the whole "said it did, didn't" framing: the lie is in the *claim*, so gating on the claim is principled, not just a cost dodge.

## Design — four pieces at verified layers

### Piece 1 — a render fingerprint computed IN the frame
**Where:** a new testable module `studio/src/frame/renderFingerprint.ts`, imported by the frame bootstrap (`frameMountPlugin.ts` `frameBootstrap`, alongside the existing `picker`/`inspector`/`gestureForwarder` imports).

**What it computes:** a hash of the *at-rest visible layout+paint* of the rendered frame — for every element under **`document.body`**, in DOM order: tag name, rounded bounding box `(x,y,w,h)`, a small fixed set of computed paint properties (`color`, `backgroundColor`, `borderTopColor`+`borderTopWidth` … 4 sides, `fontFamily`, `fontSize`, `fontWeight`, `textAlign`, `display`, `flexDirection`). Concatenate → FNV-1a 32-bit (synchronous; no async SubtleCrypto). Box coords rounded to integer px so sub-pixel jitter never flips an identical layout.

**Rev-3 — `textContent` is NOT hashed.** Rev-2 included leaf `textContent`; rev-2's own review showed that's a self-defeat: a ticking clock / `Date.now()` / any live-updating text flips the hash between two renders of identical source → the check never fires (a common frame becomes uncheckable). Geometry + paint already catch the target class (a swallowed layout/color/type prop) without reading text, so text is dropped. This trades away catching a pure text-content edit that moved no boxes (rare, and usually the boxes DO reflow) for firing at all on live frames — the right trade.

**Why `document.body`, not `#root` (rev-2 Critical fix):** the frame's own errorShim documents (`frameMountPlugin.ts:95-100`) that Radix overlays — modals `[role='dialog']`, and select/dropdown/tooltip content `[data-radix-popper-content-wrapper]` — render into a **portal on `document.body`, leaving `#root` empty**. A `#root`-only walk would read any at-rest-OPEN modal/dropdown edit as a false no-op. Walking `document.body` includes at-rest-open overlays in the hash (correct). **Exclusion (rev-3 correction — verified):** the ONLY studio-injected node that actually lands in the FRAME's `<body>` is the NWS status overlay (`[data-arcade-status-overlay]`, appended at `frameMountPlugin.ts:144`) — exclude it. The picker/inspector/gestureForwarder chrome does NOT need excluding: it injects into `document.documentElement`/`document.head` (overlays.ts, picker.ts, layoutGuides.ts) or sets attributes only (inspector.ts), never a `<body>` child — so a `document.body` walk never sees it. (Rev-2 said "exclude picker/inspector chrome"; that was an unverified assumption — corrected.)

**Why geometry AND paint (not geometry alone):** geometry alone catches the `orientation` swallow (boxes stay put) but would **false-warn on every color/typography edit** (a color change moves no boxes). Including paint props makes the fingerprint flip on any at-rest visual delta — color, type, spacing, layout — so a real visible edit always changes it. This directly serves the "never falsely claim nothing changed" bound.

**Testability (load-bearing — jsdom returns all-zero rects and stub styles, so discrimination is NOT testable against the real DOM — same class of blindness that shipped the NWS HMR bug):** the core is `computeFingerprint(root, measure)` where `measure(el) → { rect, style }` is **injected**. Production passes a `measure` built on `getBoundingClientRect()` + `getComputedStyle()`. Tests pass a synthetic `measure` returning fabricated geometry/paint, so fingerprint *discrimination* (identical layout → identical hash; any delta → different hash; DOM order sensitivity; rounding) is fully unit-tested without a real browser. The production `measure` wiring + real cross-render behavior are gated on the running-app manual gate, not claimed from unit tests.

**When it runs + how it's delivered (rev-3 — decoupled from `frame-ready`):** the fingerprint is posted as its OWN message `arcade-studio:frame-fingerprint {slug, frame, n, fp}`, NOT folded into `frame-ready`. Reason: `frame-ready` drives the double-buffer swap and must fire the instant React mounts (any delay = the visible-render swap stalls). The fingerprint needs layout AND fonts settled — `await document.fonts.ready`, then a double-`requestAnimationFrame`, THEN measure and post. So: `ArcadeFrameReady` posts `frame-ready` immediately (unchanged); a separate effect awaits fonts + rAF, computes `fp`, posts `frame-fingerprint`. FrameCard correlates the two by `n`. `document.fonts.ready` matters because `FrameFontProxy` uses `font-display:swap` — measuring before fonts load gives text geometry that shifts on the next render (a false miss). If `document.fonts` is unavailable, fall back to double-rAF only.

### Piece 2 — compare in the shell (FrameCard), reusing the double-buffer
**Where:** `studio/src/components/viewport/FrameCard.tsx`, in the existing nonce-gated `onMsg` handler that already drives the F1 double-buffer.

**Logic (pure decision extracted to a testable helper `isVisualNoOp` in a new `studio/src/components/viewport/visualNoOp.ts`).** The fingerprint arrives on the separate `frame-fingerprint` message (Piece 1); FrameCard keys handling on `editCycleActive`:

- Keep a `lastCommittedFp` ref. Also keep a per-nonce map / `pendingProbeFp` so a `frame-fingerprint` that arrives before/after the matching `frame-ready` swap can still be paired by `n`.
- **Rev-3 fix — the E self-poison (rev-2's fix was WRONG and must not be built as written).** Rev-2 said "capture fp BEFORE the gates, slug+frame only." That fires on the *probe's own* fingerprint during an edit cycle → baseline is overwritten with the probe's fp → the compare is `probeFp === probeFp` → **fires on 100% of edits.** Correct rule (verified against `FrameCard.tsx:158-202`, swap at `:180`):
  - **Capture/refresh `lastCommittedFp` ONLY when `editCycleActive.current === false`** — i.e. an at-rest committed render. This branch naturally includes the initial `n=""` first render (`editCycleActive` starts `false`, set `true` only on `frame-changed`), so E's real problem (first edit un-checkable) is solved WITHOUT bypassing the nonce/staleness protection. Nonce-match this capture against `committedNonce` (with `""↔0` normalization) so a very-late outgoing-iframe post can't write a superseded fp into the baseline.
  - **Compare** happens on an **edit-cycle** fingerprint (`editCycleActive.current === true`): `isVisualNoOp(probeFp, lastCommittedFp)` reads the PRE-EXISTING baseline (never one just overwritten by this same probe). If `lastCommittedFp != null` and equal → **visual no-op candidate** → `onVisualNoOp(frame.slug)`.
  - **Update baseline from the probe ONLY inside the swap** (after `FrameCard.tsx:180`, when the probe becomes committed) — not on fingerprint arrival.
- First generation (no prior committed fp yet) → skip. Errored edit (`frame-error`, no fingerprint) → skip (resilient-render's job).
- **`onVisualNoOp` is only a CANDIDATE** — the narration-gate (Piece 3) decides whether to retry. FrameCard can't see narration.
- **At-rest re-renders (theme toggle, resize, zoom)** run with `editCycleActive.current === false` → they only REFRESH the baseline, never compare. So a resize that moves boxes never masks a later no-op, and a theme toggle never false-registers as an edit change.
- Non-determinism → two renders differ → doesn't fire → **fails safe** (never a false warning). The `document.fonts.ready` wait + dropping live `textContent` (Piece 1) shrink this residual; see Open Q1.

### Piece 3 — corrective retry, buffered to turn-end, client-triggered, narration-gated, session-resumed
**Where:** a new middleware route `POST /api/chat/visual-noop-retry` in `studio/server/middleware/chat.ts` (mirroring the existing chat turn machinery), plus a pure-policy module `studio/server/visualNoOpRetry.ts` (mirroring `phantomEditRetry.ts`: pure policy + a server-owned corrective prompt).

**Rev-2 Critical fix — the retry must fire at TURN-END, not on `frame-ready`, and the CLIENT must trigger it.** Two real facts (verified) break the naive "server sees no-op → server retries":
1. **Frame reloads land MID-turn.** `projectWatchPlugin.ts:168-169` is a bare chokidar `all` watcher (no turn-awareness); the agent's `Edit` hits disk and fires `arcade-studio:frame-changed` *while the turn's SSE is still open*. So the client's `onVisualNoOp` candidate fires mid-turn. Triggering a retry then would either 409 against the running-turn lock (feature dead) or supersede/kill the live turn (`turnRegistry.ts:75-77`). **The client must BUFFER the no-op candidate and only act after its stream phase goes terminal** (`chatStreamReducer` `end` — `useChatStream.ts`), never on `frame-ready`.
2. **Session id persists only at turn-end.** `chat.ts:1072` writes the new `sessionId` after the turn closes; a mid-turn resume would resume the *previous* turn's session. Firing at turn-end also makes `project.sessionId` correct for the corrective's `--resume`.

**Rev-2 Important fix — the client POSTs then RECONNECTS; a server-only turn is invisible to a parked stream.** After a turn's terminal `end`, the client SSE pump PARKS on `wakeRef` (`useChatStream.ts:241`) and the server closed that response (`chat.ts:343`). A server-initiated `startTurn` does NOT wake it. So the flow is: client (after `end`, if a buffered no-op candidate exists AND the turn's narration claimed a visual change) → `POST /api/chat/visual-noop-retry {slug, frame}` → then call the existing `reconnect()` so the pump re-attaches and streams the corrective turn's narration. This reuses the exact `send()`→`reconnect()` path a normal prompt uses, so the corrective's events reach the client.
- **Rev-3 — `reconnect` must be EXPORTED.** Verified: `useChatStream` returns only `{ state, send, retry, cancel }` (`useChatStream.ts:361`); `reconnect` is a private `useCallback` (`:271`). The plan MUST add `reconnect` to the hook's return (one line) — rev-2 asserted a reachability that doesn't exist.
- **Rev-3 — fire only on an `ok`/`done` terminal end**, NOT any terminal end. The reducer maps `end`→`phase` `done|error|cancelled` (`chatStreamReducer.ts:200-237`). A turn that errors after an identical-pixel render belongs to resilient-render's error lane; gate the trigger on `phase === "done"`.
- **Rev-3 — server lock is safe.** Verified: `turnRegistry.finalize()` sets status non-running BEFORE fanning terminal `end` (`turnRegistry.ts:135-159`); `handleStart` registers the turn synchronously before its 202 (`chat.ts:275,306`). So awaiting the POST before `reconnect()` guarantees the corrective is registered and replayed, and the just-ended turn's lock is already released (no 409). Same proven ordering as `send()`.

**Why a dedicated route (not client `POST /api/chat`):** a normal chat POST paints an optimistic **user** bubble with the prompt text (`useChatStream.ts:284` `lastPrompt`). We do NOT want "your change didn't visibly render…" as a fake user message. The dedicated route runs the corrective with a **server-side** prompt (client sends only `{slug, frame}`, never prompt text), resumes `project.sessionId`, and streams narration — no user bubble. Client calls `reconnect()` (not `send()`) so no optimistic bubble is painted.

**The narration-gate is enforced where narration is authoritative.** The client holds the just-ended turn's narration. It gates the trigger: fire the retry POST ONLY if the agent made a **visual/layout claim**.
- **Rev-3 — gate on the SUMMARY LINE only, not the whole narration.** `state.narrations` (`chatStreamReducer.ts:44,168`) also accumulates SERVER lines — Figma/seeder progress, "That change didn't land — reapplying…", the deviations/no-change trailers (`chat.ts:959,993,1025`) — and the `### Deviations` body (where the agent explains what it could NOT change). Scanning all of it matches visual words in the wrong place. The response shape is contractually a one-sentence summary + `### Deviations` (`hasDeviationsSection`, `chat.ts:958`); key `narrationClaimsVisualChange` on the summary line (first non-`→` line before `### Deviations`) only.
- **Rev-3 — bias toward FIRING on doubt (reverses rev-2).** Rev-2's review showed a not-fire bias makes the gate MISS its own target class ("updated the toggles" → no keyword → the real bug ships silently). Since the self-classifying corrective (below) is a cheap catch for a false pass, but a missed target bug is the whole failure we're closing, the gate errs toward firing: fire unless the summary is clearly non-visual (pure behavior/data/a11y verbs: `wired|hooked|connected|linked|handler|clickable|accessible|aria|label|data|state|logic`) or clearly not a change (a question/refusal). Visual/layout/appearance verbs and anything ambiguous → fire. `narrationClaimsVisualChange(summaryLine)` is a pure, unit-tested function in `visualNoOpRetry.ts`, tested both directions ("now stack vertically"→fire, "wired the button to open the modal"→don't, "updated the toggles"→fire (ambiguous), a question→don't).

**The corrective prompt is SELF-CLASSIFYING (belt-and-suspenders with the narration-gate):**
> "The change you just made did not alter anything visible in the frame — the rendered result is identical to before. If it was meant to change layout or appearance and a component ignored the property (e.g. an `orientation`/variant prop the kit doesn't implement visually), achieve the intent a different way — real layout/utility classes on a wrapper, a different component — so it actually renders. If the change was intentionally non-visual (wiring behavior, an accessibility attribute, a data field), that's fine: reply saying so in one line and make no further edit. Keep the response shape (one-sentence summary + `### Deviations`)."

Even past the narration-gate, this lets the agent opt out if the gate mis-fired, instead of being forced to churn.

**One-shot — loop-safety keying (rev-3, tightened).** The corrective turn's OWN narration will typically also claim the visual change ("now stack vertically…") and its render can again be a no-op → the narration-gate would pass again → without a correct guard this LOOPS. Two coordinated guards:
- **Client:** a ref marking "a visual-noop-retry has been dispatched for the current user-turn lineage." It is set when the client POSTs, and the client treats the **corrective turn's** terminal `end` as **banner-only** — it does NOT re-evaluate the gate or POST again for that end. The ref resets only when a genuinely NEW **user** turn starts (a `send()`), never on a server-initiated corrective's `end`. (The corrective arrives via `reconnect()`, not `send()`, so it's distinguishable.)
- **Server:** the route stamps a one-shot flag keyed on the **originating user-turn id** (stable across the corrective AND any session-id rotation from `runClaudeTurnWithRetry`, `chat.ts:1003,1072`) — NOT on `sessionId` (which rotates and would defeat the flag). A second POST for the same user-turn lineage is refused.
- Net: hard stop at exactly one corrective per user turn. If the corrective's render is ALSO a no-op → straight to the banner (client), no second retry.

### Piece 4 — the honest final banner (client-side)
**Where:** a NEW sibling `studio/src/components/chat/VisualNoOpBanner.tsx` modeled on `NoFrameChangesBanner.tsx`, with its OWN distinct sentinel string. Decided (was rev-1 open): a sibling, not an extension — the two messages are different classes ("no file changed" vs "file changed, screen didn't") and keeping sentinels distinct guarantees they never collide in the persisted-message split.

**When:** after the corrective turn re-renders, if the frame is **still** a visual no-op → surface a soft, non-accusatory line: *"This change updated the code but nothing on screen moved — the setting may be one this component ignores. If you expected a visual change, try describing the look you want."* Non-blocking, informational — matches the user's F4 bar ("clearly communicate what's going on, and I know what to do"). If the retry DID move pixels → silent success (no banner).

## Data flow (end to end, rev-3)
1. Frame renders (initial AND every edit) → posts `frame-ready` immediately (drives the swap, unchanged). Separately: `await document.fonts.ready` + double-rAF → `renderFingerprint` walks `document.body` (geometry+paint, NO textContent) → posts `arcade-studio:frame-fingerprint {slug, frame, n, fp}`.
2. FrameCard: on a `frame-fingerprint` with `editCycleActive===false` (at-rest, incl. the initial `n=""` render, nonce-matched to `committedNonce`) → REFRESH `lastCommittedFp`. On one with `editCycleActive===true` (probe of an in-flight edit) → `isVisualNoOp(probeFp, lastCommittedFp)` against the PRE-EXISTING baseline → if equal, `onVisualNoOp(frame.slug)` (a CANDIDATE). Baseline is updated from the probe ONLY inside the swap (`:180`), never on fingerprint arrival — this is the fix for the rev-2 self-poison.
3. Chat controller **buffers** the candidate (does NOT act mid-turn — reloads land mid-turn). On the turn's terminal `end` with `phase==="done"`: if a candidate is buffered AND `narrationClaimsVisualChange(summaryLine)` → `POST /api/chat/visual-noop-retry {slug, frame}`, then `reconnect()`. Client one-shot ref set (per user-turn lineage). No visual claim → drop the candidate (behavior edit — correct).
4. Server route: one-shot guard keyed on the originating user-turn id → resume `project.sessionId` (persisted at turn-end) → run corrective turn with the server-side self-classifying prompt → narration streams to the reconnected client (no user bubble).
5. Corrective turn writes (or declines) → frame re-renders → FrameCard re-checks → its `end` is treated by the client as **banner-only** (never re-POST). Still a no-op → soft banner (hard stop at one). Pixels moved → silent success, no banner.

## Why this matches the user's priority
- Directly on "said it did, didn't" — the exact failure the manual gate hit, one class deeper than feature 5.
- Reuses shipped systems (double-buffer, frame-ready, session resume, the phantom-retry *shape*) rather than new infra.
- Strictly cheaper than the fidelity keystone: binary "anything moved," no vision model, no target comparison, no scoring.

## Non-goals (explicit)
- Fidelity/pixel-scoring against a design (the keystone). — separate, heavy, still unbuilt.
- Fixing the kit ToggleGroup `orientation` gap. — real but independent; this feature closes the *class*, not that one component.
- Catching wrong-but-visible changes (blue vs red). — pixels moved; out of scope by construction.
- Static prop typechecking. — feature 5's territory; this is runtime-render.

## Open questions (resolve in the plan)
1. **The "never-fires" risk (bigger than false-fire — reviewer's headline):** a frame with any non-determinism — a live clock, `Date.now()`, an animation mid-flight, a web font that swaps after `frame-ready`, an `<img>`/chart that paints late — makes two renders of identical source differ, so the fingerprint never matches and the check silently never fires. This "fails safe" (no false warning) but could make the feature a near-no-op on rich frames. **Mitigations to settle in the plan:** (a) await `document.fonts.ready` before measuring (there's no such await in frame-land today — `FrameFontProxy` uses `font-display:swap`, so text geometry shifts as fonts load); (b) the narration-gate already narrows the trigger set to "agent claimed a visual change," so the residual only matters on frames that ALSO have live non-determinism AND a swallowed visual prop — a small set; (c) accept the miss (safe direction) and rely on the soft banner only when it does fire. Decide how far to push (a).
2. **Paint-prop set + perf:** `getComputedStyle` per element × N forces style resolution, now over `document.body` (larger than `#root`). Confirm the fixed prop set catches the real deltas (color/type/spacing/layout) and measure cost on a realistic frame (few hundred elements). If too slow, cap element count (and `log`/note the cap — no silent truncation) or sample; decide in the plan.
3. **`narrationClaimsVisualChange` matcher quality:** the keyword classifier is the load-bearing gate. Enumerate the visual-claim vocabulary + the behavior-claim vocabulary from real narration samples; bias toward NOT firing on ambiguity. Decide the exact word set + whether to also require the summary to be a change-claim (not a question/refusal). Unit-test both directions.
4. **Multi-frame turns:** an edit touching frame A but not B — B legitimately unchanged. The `editCycleActive` gate already ensures only a frame whose OWN source changed (fired `frame-changed`) enters an edit cycle, so an untouched frame never produces a candidate. Confirm in the plan; buffer candidates per-frame, POST per-frame if needed (or just the first — decide).
5. **Interaction with the existing phantom-edit (file) retry:** complementary (file-no-move vs file-moved-pixel-no-move), different times (phantom INSIDE the server turn before it closes; visual AFTER the client sees terminal `end` + re-render). No double-retry: if no file moved, the frame doesn't re-render, so there's no new fp to compare → visual check can't fire. If a file DID move but pixels didn't, phantom is silent (file moved) and only visual fires. Confirm the ordering holds.
6. **Corrective-turn session freshness:** the corrective runs in a SEPARATE request after turn-end, resuming `project.sessionId` (persisted at `chat.ts:1072`). Confirm the resumed session still has the frame context (it's the same session that just did the edit — should be intact) and that a user typing a NEW prompt between turn-end and the auto-POST cleanly cancels the buffered candidate (client guard resets per user turn; the new turn takes the lock).
